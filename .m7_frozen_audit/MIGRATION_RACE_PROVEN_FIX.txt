1. THE DEFECT

--------------------------------------------------------------------------------
2. STRUCTURAL PRE-CONDITIONS  (all three must hold; all three do)
--------------------------------------------------------------------------------
(a) Lazy open. `AppDatabase.defaults()` -> `driftDatabase(name: 'next_transfer')`
    is a LazyDatabase over a background-isolate NativeDatabase. The file is
    opened by the FIRST query, not at construction.
(b) The migration is a write transaction. `onUpgrade`'s entire body is wrapped in
    `await transaction(() async { ... })` (app_database.dart:1524) which issues
    BEGIN IMMEDIATE.
(c) Three independent connections to the SAME file exist in one process:
      lib/main.dart:72
      lib/features/notifications/application/reminder_background_runtime.dart:104
      lib/features/notifications/application/reminder_background_runtime.dart:203
    Each `AppDatabase.defaults()` creates its OWN connection.

=> If any one of them issues a query while another is mid-migration, the second
   connection's BEGIN IMMEDIATE collides with the first's and SQLite returns
   SQLITE_BUSY (5).

4a. THE WITHDRAWN CLAIM  (audit integrity)
--------------------------------------------------------------------------------
The first revision of this file cited a probe "Q5" that appeared to show
busy_timeout = 5000 resolving the race, and recommended shipping it. THAT WAS
INVALID. The Q5 probe read `PRAGMA busy_timeout` on BOTH connections BEFORE the
race; those reads forced each connection to open — and therefore to migrate —
sequentially, so there was no race left to lose. Q5 measured a serialized open,
not a fixed race.

Probe 2 removes the pre-race reads and re-runs the remedies honestly:
  Q6  busy_timeout = 5000 only .............. THREW SqliteException(5)
  Q7  busy_timeout + journal_mode = WAL ..... THREW SqliteException(5)
  Q8  journal_mode = WAL only ............... THREW SqliteException(5)
None of them resolves the race. The "busy_timeout is the fix" claim is
WITHDRAWN, and the `setup:`/`CommonDatabase` half of the old patch was removed.

WHY NO TIMEOUT CAN HELP (the actual mechanism):
the two connections deadlock on lock UPGRADES. A holds RESERVED
(BEGIN IMMEDIATE) and needs EXCLUSIVE to commit; B holds SHARED (from reading
user_version) and needs RESERVED. Neither can yield, so SQLite raises
SQLITE_BUSY, and a lock-upgrade conflict does NOT invoke the busy handler at all.

--------------------------------------------------------------------------------
5. THE CORRECTIVE ACTUALLY APPLIED  (one constant, one call site)
--------------------------------------------------------------------------------
drift already provides a first-class remedy for exactly this pattern.
`DriftNativeOptions.shareAcrossIsolates` (drift_flutter 0.3.1,
lib/src/connect.dart:52) documents:

    "When using a shared instance, stream queries synchronize across the two
     isolates. Also, drift then manages concurrent access to the database,
     preventing 'database is locked' errors due to concurrent transactions."
    "This option is not enabled by default, but RECOMMENDED IF A DRIFT DATABASE
     MAY BE USED ON MULTIPLE ISOLATES."

APPLIED at lib/core/database/app_database.dart:1415, in `AppDatabase.defaults()`:

    +  const DriftNativeOptions kAppDatabaseNativeOptions = DriftNativeOptions(
    +    shareAcrossIsolates: true,
    +  );
    ...
    -  super(driftDatabase(name: 'next_transfer'));
    +  super(driftDatabase(name: 'next_transfer', native: kAppDatabaseNativeOptions));

All three `AppDatabase.defaults()` sites go through that constructor, so they now
converge on ONE shared connection and a second connection can no longer race the
migration's BEGIN IMMEDIATE. NOTE: the constant deliberately carries NO `setup:`
callback, because a connection-level busy_timeout was MEASURED NOT TO WORK
(section 4a).

WHY THIS IS NARROW:
  - one call site plus one constant
  - no schema change (still exactly 47)
  - no migration-logic change (the three v47 hunks are untouched)
  - no change to beforeOpen, onUpgrade, or the transaction wrapper
  - no new dependency (drift_flutter is already a dependency)
  - `AppDatabase.forTesting` is unaffected (no test calls `defaults()`), so every
    existing database test keeps its executor and behaviour

HONEST LIMIT: `shareAcrossIsolates` shares within ONE Flutter engine (it resolves
the connection through `IsolateNameServer`). It removes the three same-engine
connections that caused this startup failure. A separate engine (e.g. a
WorkManager isolate in its own engine) would need a different remedy, and none is
introduced here.
