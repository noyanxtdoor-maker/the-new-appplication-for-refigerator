Q4 — Are read/merge/write ops transactional enough to prevent lost updates?

  PARTIAL. Each writer wraps its read-modify-write in database.transaction(),
  and drift runs nested transaction blocks in the current transaction zone,
  so a single writer's own read→write is atomic. That is sufficient to stop
  two writers of the SAME key from interleaving mid-operation.

  It is NOT sufficient for cross-key safety, because the defect in Q3 is not
  a race — it is an unconditional KEY DROP inside a successfully committed
  transaction. Serialising W2 cannot help; the data is deleted either way.

Q5 — Can A (notification read) → B (Event Color write) → C (notification
     stale write) lose settings?

  TWO DISTINCT LOSSES, and ONLY ONE OF THEM IS ACTUALLY REACHABLE:

  (5a) REACHABLE — the dominant case. Any Event Color save at B deletes the
       notification key with immediate effect, whether or not C ever runs.
       The user's five Detailed-content switches silently revert to the
       all-true defaults on the next read (fail-closed default in
       DetailedContentPreferences.fromJson). Reproduced in Probe 1.

  (5b) NOT REACHABLE in the current production wiring. A stale notification
       write at C would need W1 to hold a snapshot taken before B and then
       blindly overwrite the whole document. It does not: W1 re-SELECTs the
       raw column INSIDE its transaction, merges, and writes. Because both W1
       (and, in-process, W2) participate in drift's transaction zone, an
       in-process A→B→C sequence serialises, so W1 re-reads B's result and
       preserves the Event Color change. I must be explicit here: this is
       proven by reading the transaction structure, NOT re-measured with a
       dedicated two-writer concurrency probe. Treat 5b as NOT PROVEN.
       A cross-process ordering (for example a background reminder isolate
       writing while the UI writes) is outside what W1's in-transaction
       re-read alone can guarantee.

  Bottom line for Q5: the notification settings ARE lost, by (5a), which is
  an ordinary single-user action sequence and is empirically reproduced.
