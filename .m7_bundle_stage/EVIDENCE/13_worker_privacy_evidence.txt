WORKER PRIVACY AUDIT (Contract section 14-17)
================================================================================
Consumer of this evidence: independent GLM-vs-DeepSeek comparison.

--------------------------------------------------------------------------------
REQUIREMENT
--------------------------------------------------------------------------------
A background worker's input payload and any DURABLE metadata it persists must
contain ONLY technical identifiers. It must NEVER persist private notification
content. Private content must be reread from the source of truth at DELIVERY
time.

Specifically forbidden from worker input / durable metadata:
    - Contact names
    - Event titles
    - Task titles
    - Descriptions
    - Notes
    - Location text
    - Any rendered/display string

--------------------------------------------------------------------------------
PART 1 — WORKER INPUT PAYLOAD
--------------------------------------------------------------------------------
File: lib/core/background/workmanager_background_work_gateway.dart

The permitted input field set is closed and contains exactly three technical
identifiers:
    stable_key        -> the stable reminder identity
    scheduled_utc_ms  -> the normalized scheduled target (epoch millis)
    source_revision   -> the technical revision token

Enforcement is reject-by-default, not filter-by-default:
    if (input == null || input.length != allowedFields.length) return null;
    if (input.keys.any((key) => !allowedFields.contains(key))) return null;

=> An extra key of ANY name causes the entire payload to be rejected. There is
   no path by which a display string can ride along into the worker.

The stable key is further bounded by a restrictive grammar:
    ^reminder:[A-Za-z0-9_.:-]{1,240}$
This admits only `reminder:` followed by identifier characters — no spaces, no
punctuation beyond `_.:-`, so it cannot carry human-readable content.

Result:

Files covered by that scan (all of lib/core/background/):
    background_repair_decision.dart
    background_work_gateway.dart
    background_work_request.dart
    reminder_recovery_request.dart

The durable repair-marker row (see EVIDENCE/11_repair_marker_evidence.txt) stores
only: stableKey, category, ownerKind, occurrenceId, platformNotificationId,
state, attemptCount, snoozeCount, sourceRevision, createdAtUtc. Every one of
these is a technical identifier or a counter/timestamp. No private content.

--------------------------------------------------------------------------------
PART 3 — DELIVERY-TIME REREAD
--------------------------------------------------------------------------------
File: lib/features/notifications/application/reminder_enrichment_resolver.dart
File: lib/features/notifications/data/drift_reminder_enrichment_source.dart
File: lib/features/notifications/application/reminder_notification_renderer.dart

Enrichment (Contact name, location text) and rendering both happen AT DELIVERY
TIME, reading from the database at that moment. The worker carries only the
identifier needed to locate the source rows. This is what makes CONTACT FRESHNESS
possible (Contract section 66): a renamed or invalidated Contact is reflected in
the next delivery rather than served from a stale persisted copy.

Sanitization applied at enrichment (Contract section 15):
    maxNameGraphemes     = 80      (grapheme clusters, not code units)
    maxLocationGraphemes = 120

Rejected from location text:
    - control and bidirectional-override characters (_bidiControls regex)
    - URI / scheme-like prefixes such as https:, geo:, google.navigation:
    - bare decimal latitude/longitude pairs
    - degree-symbol coordinate forms

The grapheme-based bound matters: a code-unit bound would truncate multi-byte
emoji and combining sequences mid-cluster, producing broken output and a possible
mismatch between what was measured and what was rendered.
