K. MIGRATION-STARTUP RACE — ROOT CAUSE + CORRECTIVE
================================================================================
STATUS: ROOT CAUSE CONFIRMED, REPRODUCED OFF-DEVICE, AND CORRECTED.
The corrective IS APPLIED in this tree (lib/core/database/app_database.dart). See K4.

K1. The defect
On the first launch after a v46 -> v47 upgrade the app hangs permanently on the
Android splash screen (no frame, no ANR, process alive). Logcat:
  Unhandled Exception: SqliteException(5): while executing, database is locked
  Causing statement: BEGIN IMMEDIATE
  at app_database.dart:1524:9  AppDatabase.migration.<fn>
The database itself is healthy: user_version 46 -> 47, integrity_check ok,
3986 rows preserved, zero row loss.

K2. Mechanism  (as it was BEFORE the corrective; line numbers are post-corrective)
1. The connection is lazy: `AppDatabase.defaults()` ->
   `super(driftDatabase(name: 'next_transfer', native: kAppDatabaseNativeOptions))`
   (app_database.dart:1415; pre-corrective it was a bare
   `driftDatabase(name: 'next_transfer')`).
   `driftDatabase` is drift's LazyDatabase + background-isolate NativeDatabase;
   the file is opened on the FIRST query, not at construction.
2. The first query on the startup path is
   `DatabaseBootstrap.verifyOpen()` -> `PRAGMA quick_check`
   (database_bootstrap.dart:15-17), called from
   `drift_startup_repository.dart:205`.
3. That lazy open detects stored v46 vs code v47 and runs `onUpgrade`, whose
   ENTIRE body is wrapped in `await transaction(() async { ... })` at
   app_database.dart:1524. `transaction()` issues `BEGIN IMMEDIATE` — an
   exclusive write lock.
4. `AppDatabase.defaults()` is constructed at THREE independent sites, each an
   independent connection to the same file:
     lib/main.dart:72
     lib/features/notifications/application/reminder_background_runtime.dart:104
     lib/features/notifications/application/reminder_background_runtime.dart:203
   If any other connection is open or reading at that instant, `BEGIN IMMEDIATE`
   cannot acquire the lock -> SqliteException(5). The exception is unhandled on
   the startup path, so Flutter never draws a frame -> permanent splash.
5. The second launch succeeds because `user_version` is already 47, so
   `onUpgrade` is never entered (proved on device: clean
   startup_initialize -> database_open_started -> database_open_ready ->
   startup_resolved, no migration markers, COLD start 3208 ms).

K3. v47 TRIGGERED it; it did not author it
`git diff 7b1395c -- lib/core/database/app_database.dart` has five hunks (see J):
three are the v47 schema change, two are the corrective itself. Among the THREE
SCHEMA hunks, neither `onUpgrade`'s transaction wrapper, nor `beforeOpen`, nor
the open path is touched. Before this upgrade the stored schema already equalled
the code version, so `onUpgrade` never ran and the latent race was never
exercised. Classification: PRE-EXISTING LATENT DEFECT, FIRST EXPOSED BY v47.

K4. REPRODUCED OFF-DEVICE; THE CORRECTIVE IS APPLIED
Probes: .m7_frozen_audit/migration_race_probe/zz_migration_race_probe_test.dart,
        .../zz_migration_race_probe2_test.dart,
        .../zz_migration_race_probe3_test.dart
(all live OUTSIDE test/, so they cannot enter the suite or the differential.)

  Q1  effective PRAGMA on a default AppDatabase connection:
        busy_timeout = 0        <-- no wait at all
        journal_mode = delete ; foreign_keys = 1
  Q2  a competing writer        -> THREW SqliteException(5) "database is locked"
  Q3  v46 -> v47 race, as shipped:
        A = OK ;  B = THREW SqliteException(5) ... BEGIN IMMEDIATE ;
        final user_version = 47
      ^ the DEVICE FAILURE, reproduced deterministically off-device.

MECHANISM (this is why no timeout can help): the two connections deadlock on
lock UPGRADES. A holds RESERVED (BEGIN IMMEDIATE) and needs EXCLUSIVE to commit;
B holds SHARED (from reading user_version) and needs RESERVED. Neither can yield,
so SQLite raises SQLITE_BUSY, and a lock-upgrade conflict does not invoke the
busy handler at all.

REMEDIES THAT WERE MEASURED AND REJECTED (probe 2):
  Q6  busy_timeout = 5000 only .............. THREW SqliteException(5)
  Q7  busy_timeout + journal_mode = WAL ..... THREW SqliteException(5)
  Q8  journal_mode = WAL only ............... THREW SqliteException(5)
None of them resolves the race.

PRODUCTION-PATH PROOF (probe 3) — Q1-Q8 use a hand-built `NativeDatabase`, which
proves the mechanism but not that the REAL production entry point behaves the
same way. Probe 3 therefore drives `driftDatabase(name: 'next_transfer',
native: ...)` itself — the exact call `AppDatabase.defaults()` makes — and
observes the connection-sharing registry directly. Evidence:
.m7_frozen_audit/migration_race_probe/PROBE3_PRODUCTION_PATH.txt

  Q9  CONTROL — production entry point, drift's DEFAULT options, two connections
      racing the v46 -> v47 migration:
        THREW SqliteException(5): "database is locked",
        Causing statement: BEGIN IMMEDIATE        <-- THE DEVICE FAILURE,
                                                      via the production path
      (surfaced as a DriftRemoteException wrapping the SqliteException, because
       `driftDatabase` runs the connection in a background isolate)
  Q10 CORRECTIVE — the same two connections WITH shareAcrossIsolates: true:
        OK ;  final user_version = 47
  Q11 CAUSAL CONTRAST — direct observation of the sharing registry:
        IsolateNameServer port 'drift-db/next_transfer'
          WITHOUT shareAcrossIsolates ....... ABSENT
          WITH    shareAcrossIsolates ....... PRESENT
      This is the mechanism itself, observed — not inferred from timing.

Probe 3 = ALL ASSERTIONS PASS. So the corrective is proven to change the
production code path, not merely an adjacent one.

CORRECTION LOGGED (audit integrity): an earlier probe pass (its "Q5") appeared to
show that a busy_timeout resolved the race, and that was briefly written up as a
proven fix. It was WRONG: that probe read `PRAGMA busy_timeout` on BOTH
connections BEFORE the race, and those reads forced each connection to open — and
therefore to migrate — sequentially, so there was no race left to lose. Probe 2
removes the pre-race reads and shows all three timeout/WAL remedies failing. The
"Q5 proves a busy_timeout works" claim is WITHDRAWN.

THE CORRECTIVE ACTUALLY APPLIED — remove the second connection.
drift provides the remedy directly. `DriftNativeOptions.shareAcrossIsolates`
(already-available dependency drift_flutter 0.3.1) makes every
`driftDatabase(name: 'next_transfer')` in the process converge on ONE shared
connection. Drift documents it as managing "concurrent access to the database,
preventing 'database is locked' errors due to concurrent transactions" and
"recommended if a drift database may be used on multiple isolates".

  lib/core/database/app_database.dart
    + const DriftNativeOptions kAppDatabaseNativeOptions = DriftNativeOptions(
    +   shareAcrossIsolates: true,
    + );
    ...
    -   super(driftDatabase(name: 'next_transfer'));
    +   super(driftDatabase(name: 'next_transfer', native: kAppDatabaseNativeOptions));

All three `AppDatabase.defaults()` sites (lib/main.dart:72,
reminder_background_runtime.dart:104 and :203) go through that constructor, so
they now share one connection and a second connection can no longer race the
migration.

WHY IT IS NARROW: one call site plus one constant; schema still exactly 47; the
v47 migration hunks, `onUpgrade`, `beforeOpen` and the `transaction(...)` wrapper
are all untouched; no new dependency; `AppDatabase.forTesting` is unaffected (no
test calls `defaults()`), so every existing database test keeps its executor.

HONEST LIMIT: `shareAcrossIsolates` shares within ONE Flutter engine (it resolves
the connection through `IsolateNameServer`). It removes the three same-engine
connections that caused this startup failure. A separate engine (e.g. a
WorkManager isolate in its own engine) would need a different remedy, and none is
introduced here.
